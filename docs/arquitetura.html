SISTEMAS OPERACIONAIS · AVALIAÇÃO M1 · IPC, THREADS E PARALELISMO

minidb-ipc — desenho do sistema

Gerenciador de requisições a um banco de dados simulado: um processo cliente produz requisições em memória compartilhada POSIX, um processo servidor as consome com um pool de threads e aplica cada operação sobre uma tabela protegida por um lock de leitores-escritores construído com pthread_mutex_t + sem_t. As respostas voltam por um segundo canal IPC (FIFO nomeado) e são registradas em log.

C++17 pthreads POSIX shm sem_t nomeado FIFO (mkfifo) 2 binários implementado

FIGURA 1

Fluxo do sistema

Requisição percorre a metade de cima da esquerda para a direita; a resposta volta pela metade de baixo. A coluna do meio é a fronteira entre os dois processos: tudo que a atravessa é objeto do kernel, nunca variável global nem chamada de função.

  1. O cliente lê a carga (arquivo ou gerador) e o parser converte SELECT nome WHERE id=5 em uma Requisicao de tamanho fixo.
  2. A thread produtora faz sem_wait(vazias), entra no sem_mutex_ring, copia a struct no slot e faz sem_post(cheias).
  3. A thread despachante do servidor faz sem_wait(cheias), retira o slot e devolve espaço com sem_post(vazias).
  4. A requisição vai para a fila interna do servidor; a thread despachante volta imediatamente ao ring.
  5. Os N workers do pool acordam na condvar e retiram tarefas da fila em paralelo.
  6. SELECT entra como leitor: vários workers leem a tabela simultaneamente.
  7. INSERT, UPDATE e DELETE entram como escritores: acesso exclusivo à tabela.
  8. O worker monta a Resposta com status, dados e tempo de espera no lock.
  9. A resposta é escrita no FIFO (uma escrita por vez, protegida por mutex) e replicada no log.
  10. A thread receptora do cliente lê a resposta, confere contra a requisição e imprime.

FIGURA 2

O que o lock de leitores-escritores compra

Este é o ponto do trabalho que precisa ser medido e defendido na apresentação: um mutex único serializaria tudo; o lock de leitores-escritores deixa os SELECT correrem juntos e só serializa quando aparece uma escrita.

FIGURA 3 · MEDIÇÃO

O que o sistema entrega na prática

Medido em uma máquina de 4 núcleos, 10.000 requisições por execução, mediana de 3 repetições, com um custo de processamento simulado de 200 µs por requisição — sem esse custo o trabalho por requisição é tão curto que a medição vira um teste do IPC, não do pool.

A coluna da espera no lock é a que fecha o argumento: na carga de leitura ela fica em décimos de microssegundo por mais threads que existam — os leitores entram juntos. Na carga de escrita ela cresce proporcionalmente ao número de threads, porque cada escritor espera todos os anteriores. É o mesmo fenômeno da figura 2, agora em número.

Sem custo simulado (--custo-us 0) o resultado se inverte: uma thread rende ~105.000 req/s e mais threads pioram para ~40.000. Com trabalho de poucos nanossegundos por requisição, o custo de sincronizar as threads supera o que o paralelismo economiza — o gargalo passa a ser o IPC, não o banco. Vale registrar isso no relatório: é a lei de Amdahl aparecendo na prática, e não um defeito da implementação.

CONTRATO

O que precisa estar fechado primeiro

Structs POD de tamanho fixo, sem ponteiros e sem std::string: um slot do ring e uma mensagem do FIFO são cópias byte a byte, então o mesmo cabeçalho vale para os dois binários.

// include/common/protocolo.hpp
enum class Op     : uint8_t { INSERT, DELETE, SELECT, UPDATE };
enum class Status : uint8_t { OK, NAO_ENCONTRADO, ID_DUPLICADO, TABELA_CHEIA, MALFORMADA };

struct Requisicao {   // cliente → servidor, via ring na memória compartilhada
    uint32_t id_req;      // correlaciona requisição e resposta
    int32_t  pid_cliente; // permite vários clientes no mesmo ring
    Op       op;
    int32_t  id;          // chave do registro
    char     nome[50];    // carga útil de INSERT / UPDATE
};

struct Resposta {     // servidor → cliente, via FIFO nomeado
    uint32_t id_req;
    Status   status;
    Registro registro;    // preenchido em SELECT
    uint64_t us_no_lock;  // tempo esperando o lock — alimenta as métricas
    uint32_t worker;      // qual thread do pool atendeu
};

DIVISÃO

Três frentes, um contrato

O trio fecha junto common/protocolo.hpp e common/config.hpp; a partir daí cada frente compila e testa a sua camada isoladamente.

Frente 1 — IPC

  • shm_region, named_sem
  • shm_ring (produtor-consumidor)
  • fifo_channel
  • tests/test_ipc.cpp
  • Apresenta: shm_open, mmap, sem_open, mkfifo

Frente 2 — Concorrência

  • rw_lock, banco
  • fila_tarefas, pool_threads
  • executor, persistencia
  • test_rw_lock, test_corrida
  • Apresenta: seção crítica, condição de corrida, deadlock evitado

Frente 3 — Cliente e medição

  • parser, gerador_carga
  • cliente/main.cpp
  • metricas, scripts/
  • CSVs, gráficos e tabelas
  • Apresenta: resultados, escalabilidade por nº de threads

EXECUÇÃO

Como rodar

Só precisa de g++ com C++17 e um Linux com POSIX shm e semáforos nomeados. Nenhuma dependência externa.

# compila os dois binários
make

# demonstração ponta a ponta: sobe o servidor, roda um cliente, mostra o log
make demo

# manualmente, em dois terminais
./bin/servidor --threads 4
./bin/cliente  --carga data/cargas/basica.txt

# vários processos cliente disputando o mesmo ring
./scripts/multi_cliente.sh 4 500

# os três testes
make testes && ./bin/test_ipc && ./bin/test_rw_lock && ./bin/test_corrida

# bateria de medições + gráficos do relatório
./scripts/benchmark.sh && python3 scripts/plot.py

O servidor encerra com Ctrl+C ou SIGTERM: o sinal interrompe o sem_wait da thread despachante, que fecha a fila, espera os workers drenarem o que sobrou, salva o banco e remove a memória compartilhada, os semáforos e os FIFOs. Se algum processo for morto com -9 e deixar objetos de kernel para trás, make limpar-ipc resolve.

  • Deixar o repositório público

Limites conhecidos

  • Busca linear na tabela: O(n) por requisição, suficiente para a escala do trabalho
  • Requisições de um mesmo cliente são atendidas em paralelo, então não há ordem garantida entre elas
  • A tabela vive em memória; o arquivo é gravado só no encerramento
