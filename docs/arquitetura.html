SISTEMAS OPERACIONAIS · AVALIAÇÃO M1 · IPC, THREADS E PARALELISMO

Banco de dados com IPC e threads

Dois programas separados: o cliente envia requisições por memória compartilhada e o servidor as executa com quatro threads sobre uma tabela protegida por mutex. O resultado de cada requisição vai para um arquivo de log.

C pthreads memória compartilhada semáforos mutex 5 arquivos

FLUXO

O caminho de uma requisição

A requisição desce a coluna de cima para baixo. A memória compartilhada é a única ligação entre os dois processos — nenhum deles chama função do outro.

ESTRUTURA

Os arquivos do projeto

├── cliente.c     programa 1: monta as requisições e escreve na memória compartilhada
├── servidor.c    programa 2: cria a memória, sobe as 4 threads e executa na tabela
├── banco.h      structs e constantes que os dois programas precisam conhecer
├── banco.txt    os dados salvos, no formato id;nome
├── Makefile     compila os dois programas
└── log.txt      gerado: o que cada thread fez

banco.h existe porque cliente e servidor são processos separados e precisam concordar sobre o formato exato das estruturas que atravessam a memória compartilhada. Se um deles mudasse a struct Requisicao, o outro leria os bytes errados.

EXECUÇÃO

Como rodar

Precisa de Linux e gcc. No Windows, use o WSL.

make

# terminal 1
./servidor

# terminal 2 (com o servidor já no ar)
./cliente

No VS Code, Ctrl+Shift+5 divide o terminal integrado em dois painéis — um para cada programa. O servidor imprime linha a linha o que cada thread está fazendo; como há uma pausa proposital dentro da seção crítica, dá para acompanhar o revezamento na tela.

CONCEITOS

Os três pontos da matéria, no código

/* 1. IPC — o cliente escreve na memória compartilhada (cliente.c) */
sem_wait(sem_vazias);              /* espera ter slot livre     */
sem_wait(sem_mutex);               /* entra na região do buffer */
buffer->requisicoes[buffer->fim] = req;
buffer->fim = (buffer->fim + 1) % MAX_REQUISICOES;
sem_post(sem_mutex);
sem_post(sem_cheias);              /* avisa que chegou trabalho */


/* 2. Threads — o servidor cria o pool (servidor.c) */
for (i = 0; i < NUM_THREADS; i++) {
    numeros[i] = i;
    pthread_create(&threads[i], NULL, trabalhador, &numeros[i]);
}


/* 3. Exclusão mútua — a seção crítica (servidor.c) */
pthread_mutex_lock(&mutex_tabela);     /* ---- entra ---- */

switch (req.op) {
    case INSERT: op_insert(req.id, req.nome, resultado); break;
    case SELECT: op_select(req.id, resultado);           break;
    case UPDATE: op_update(req.id, req.nome, resultado); break;
    case DELETE: op_delete(req.id, resultado);           break;
}

pthread_mutex_unlock(&mutex_tabela);   /* ---- sai ------ */

Sem o pthread_mutex_lock, duas threads poderiam inserir ao mesmo tempo: as duas leriam total_registros com o mesmo valor, escreveriam na mesma posição do vetor e um dos registros seria perdido. É exatamente a condição de corrida que a exclusão mútua evita.

PARA A APRESENTAÇÃO

Duas perguntas prováveis

  1. Por que três semáforos e não um? Cada um resolve um problema diferente: vazias e cheias fazem os processos esperarem sem gastar CPU (buffer cheio e buffer vazio), e mutex impede que cliente e servidor mexam nos índices inicio e fim ao mesmo tempo.
  2. As requisições são executadas na ordem em que foram enviadas? Não. As quatro threads pegam requisições em paralelo, então a ordem entre elas não é garantida — é consequência direta do paralelismo que o trabalho pede. O que o mutex garante é que a tabela nunca fique inconsistente.
